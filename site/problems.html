ExpiredToken: the security token included in the request is expired

Error text

An error occurred (ExpiredToken) when calling the GetCallerIdentity operation: The security token included in the request is expired

Why it happens

The temporary credentials the CLI sent (from assume-role, SSO or an instance role) have passed their expiry time.

Likely causes

  • Old AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY and AWS_SESSION_TOKEN left in the environment
  • An SSO session that has run out
  • A long job outliving a one-hour role session

Confirm

aws configure list
env | grep AWS_

Fix

  • Unset the stale variables: unset AWS_ACCESS_KEY_ID AWS_SECRET_ACCESS_KEY AWS_SESSION_TOKEN
  • Sign in again: aws sso login --profile <profile>
  • For long jobs, let the SDK refresh credentials from a profile or role instead of pasting them

Prevent it

  • Use profiles with SSO or role_arn, not pasted session variables
  • Raise the role's MaxSessionDuration if jobs legitimately run longer

InvalidClientTokenId: the security token included in the request is invalid

Error text

An error occurred (InvalidClientTokenId) when calling the GetCallerIdentity operation: The security token included in the request is invalid.
An error occurred (InvalidAccessKeyId) when calling the ListBuckets operation: The AWS Access Key Id you provided does not exist in our records.

Why it happens

AWS does not recognise the access key ID: it was deleted, deactivated, mistyped, or is a session key sent without its session token.

Likely causes

  • The key was deleted or set Inactive
  • A session key (ASIA...) without AWS_SESSION_TOKEN
  • Calling an opt-in Region that is not enabled for the account

Confirm

aws configure list
aws iam list-access-keys --user-name <user>

Fix

  • Use a profile with valid credentials (--profile), or create a new key for the user
  • Set AWS_SESSION_TOKEN alongside session keys

Prevent it

  • Prefer roles and SSO to long-lived access keys

SignatureDoesNotMatch

Error text

An error occurred (SignatureDoesNotMatch) when calling the GetCallerIdentity operation: The request signature we calculated does not match the signature you provided. Check your AWS Secret Access Key and signing method. Consult the service documentation for details.

Why it happens

The access key ID exists, but the request was signed with a different secret, or the clock is wrong.

Likely causes

  • A secret access key copied with a missing or extra character
  • The secret of a different key paired with this key ID
  • The machine's clock is off by more than five minutes

Confirm

aws configure list
date -u

Fix

  • Re-enter the secret with aws configure set aws_secret_access_key ... or create a new key pair
  • Sync the clock (NTP)

Prevent it

  • Use SSO or roles so no secret is copied by hand

Unable to locate credentials

Error text

Unable to locate credentials. You can configure credentials by running "aws configure".

Why it happens

The CLI looked everywhere in its chain (flags, environment, config files, container and instance roles) and found nothing.

Likely causes

  • No profile configured on this machine
  • AWS_PROFILE names a profile that has no credentials
  • An instance without a role, or with IMDS turned off

Confirm

aws configure list
aws configure list-profiles

Fix

  • aws configure sso (people) or attach an instance profile (servers)
  • Check --profile and AWS_PROFILE point at the profile you mean

Prevent it

  • Give servers roles, never keys in files

AccessDenied: no identity-based policy allows the action

Error text

An error occurred (AccessDenied) when calling the ListObjectsV2 operation: User: arn:aws:iam::111122223333:user/analyst is not authorized to perform: s3:ListBucket on resource: "arn:aws:s3:::nimbus-kitchen-reports" because no identity-based policy allows the s3:ListBucket action

Why it happens

Nothing allows this principal to do this action on this resource. The message names all three; read it to the end.

Likely causes

  • The policy allows a different action (s3:GetObject is not s3:ListBucket)
  • The policy names a different resource (bucket/* is not the bucket)
  • A condition in the policy does not match the request

Confirm

aws sts get-caller-identity
aws iam simulate-principal-policy --policy-source-arn <arn> --action-names <action> --resource-arns <arn>

Fix

  • Allow exactly that action on exactly that resource
  • Remember bucket-level actions take arn:aws:s3:::bucket and object actions take arn:aws:s3:::bucket/*

Prevent it

  • Test new policies with simulate-principal-policy or IAM Access Analyzer policy validation

AccessDenied with an explicit deny

Error text

is not authorized to perform: ec2:StopInstances on resource: arn:aws:ec2:us-east-1:111122223333:instance/i-0abc with an explicit deny in an identity-based policy
with an explicit deny in a resource-based policy

Why it happens

A Deny statement matched. An explicit deny wins over every allow, AdministratorAccess included.

Likely causes

  • A guard-rail policy with Resource "*" and no condition
  • A bucket or key policy that denies, for example, requests without TLS
  • A permissions boundary or session policy

Confirm

aws iam list-user-policies --user-name <user>
aws iam list-attached-user-policies --user-name <user>

Fix

  • Narrow the Deny with a condition or a specific resource, rather than deleting it
  • Fix the request so it meets the condition (for example, use HTTPS)

Prevent it

  • Write denies with explicit conditions and test both what they block and what they allow

UnauthorizedOperation with an encoded authorization failure message

Error text

An error occurred (UnauthorizedOperation) when calling the RunInstances operation: You are not authorized to perform this operation. Encoded authorization failure message: ...

Why it happens

EC2 hides which permission failed. The encoded message says, for someone allowed to decode it.

Likely causes

  • A missing permission on a related resource: iam:PassRole, kms:CreateGrant, ec2:CreateTags
  • An explicit deny

Confirm

aws sts decode-authorization-message --encoded-message <message> --query DecodedMessage --output text

Fix

  • Read action, resource and explicitDeny in the decoded JSON and grant (or narrow the deny on) exactly that

Prevent it

  • Give developers sts:DecodeAuthorizationMessage so they can read their own failures

Not authorized to perform iam:PassRole

Error text

is not authorized to perform: iam:PassRole on resource: arn:aws:iam::111122223333:role/web-role because no identity-based policy allows the iam:PassRole action

Why it happens

Giving a role to a service (an instance profile, a Lambda execution role, an ECS task role) requires permission to pass that role.

Likely causes

  • The caller can create the resource but has no iam:PassRole
  • PassRole is scoped to a different role or service

Confirm

aws iam simulate-principal-policy --policy-source-arn <caller-arn> --action-names iam:PassRole --resource-arns <role-arn>

Fix

  • Allow iam:PassRole on that role's ARN, with an iam:PassedToService condition

Prevent it

  • Never grant iam:PassRole on *: it lets the caller hand an admin role to code they control

AccessDenied when calling AssumeRole

Error text

An error occurred (AccessDenied) when calling the AssumeRole operation: User: arn:aws:iam::111122223333:user/ci-bot is not authorized to perform: sts:AssumeRole on resource: arn:aws:iam::111122223333:role/deploy-role

Why it happens

Either the caller's policies do not allow sts:AssumeRole, or the role's trust policy does not name the caller. The message is the same for both.

Likely causes

  • The trust policy names a deleted user (it shows as AIDA... or AROA...)
  • The trust policy names a different account or role
  • A condition such as sts:ExternalId or MFA is not met

Confirm

aws iam get-role --role-name <role> --query Role.AssumeRolePolicyDocument
aws sts get-caller-identity

Fix

  • Name the caller in the trust policy: aws iam update-assume-role-policy
  • Allow sts:AssumeRole on the role in the caller's policy

Prevent it

  • Trust roles rather than users, and manage trust policies in code

The OIDC token (from GitHub Actions, for example) does not match the role's trust policy.

KMS AccessDeniedException: no resource-based policy allows kms:Decrypt

Error text

An error occurred (AccessDeniedException) when calling the Decrypt operation: User: arn:aws:sts::111122223333:assumed-role/payments-app/you is not authorized to perform: kms:Decrypt on resource: arn:aws:kms:us-east-1:111122223333:key/... because no resource-based policy allows the kms:Decrypt action

Why it happens

The key policy does not allow the caller. With KMS, an IAM allow is never enough on its own.

Likely causes

  • The key policy has no statement for the role, and no root-account statement delegating to IAM
  • The object was encrypted with a different key
  • Cross-account use without both sides allowing it

Confirm

aws kms get-key-policy --key-id <key-id> --policy-name default --query Policy --output text
aws s3api head-object --bucket <bucket> --key <key>

Fix

  • Add a key policy statement for the role (or the account root, then allow it in IAM) with aws kms put-key-policy

Prevent it

  • Keep the administrators' statement in every key policy; KMS refuses policies that would lock you out

Connection timed out to an EC2 instance

Error text

curl: (28) Failed to connect to 203.0.113.10 port 80 after 75003 ms: Couldn't connect to server
ssh: connect to host 203.0.113.10 port 22: Operation timed out

Why it happens

Packets were dropped silently somewhere. Something in the path does not allow the traffic.

Likely causes

  • The security group does not allow the port from your address
  • The network ACL drops the request or the reply (ephemeral ports)
  • The subnet has no route to an internet gateway
  • The instance has no public IP, or is stopped

Confirm

aws ec2 describe-instances --instance-ids <id> --query 'Reservations[].Instances[].[State.Name,PublicIpAddress,SubnetId]'
aws ec2 describe-security-groups --group-ids <sg-id>
aws ec2 describe-route-tables --filters Name=association.subnet-id,Values=<subnet-id>
aws ec2 describe-network-acls --filters Name=association.subnet-id,Values=<subnet-id>

Fix

  • Work outward: instance state, public IP, security group, NACL (both directions), route table, internet gateway
  • VPC Reachability Analyzer can trace the path for you

Prevent it

  • Build networks from templates, and use Session Manager instead of opening SSH

Private instance cannot reach the internet

Error text

curl: (28) Failed to connect to api.github.com port 443 after 130217 ms: Couldn't connect to server

Why it happens

Instances in a private subnet reach the internet only through a NAT gateway (or a proxy).

Likely causes

  • No NAT gateway, or no 0.0.0.0/0 route to it in the private route table
  • The NAT gateway sits in a private subnet
  • Outbound blocked by the security group or NACL

Confirm

aws ec2 describe-route-tables --filters Name=association.subnet-id,Values=<subnet-id>
aws ec2 describe-nat-gateways

Fix

  • Create a NAT gateway in a public subnet with an Elastic IP, and route 0.0.0.0/0 from the private route table to it

Prevent it

  • Use gateway endpoints for S3 and DynamoDB, and interface endpoints for AWS APIs, so less traffic needs NAT

Error text

Why it happens

VPC peering active, traffic times out

Error text

Ncat: TIMEOUT.
"Status": {"Code": "active", "Message": "Active"}
"Status": {"Code": "failed", "Message": "Overlapping CIDRs"}

Why it happens

The peering connection exists, but packets have no route in one direction, or a security group drops them.

Likely causes

  • The other VPC's route table has no route back to your CIDR through the peering
  • Security groups reference addresses from the wrong VPC
  • Overlapping CIDRs: a peering between overlapping ranges cannot be created
  • Expecting transit: peering is not transitive

Confirm

aws ec2 describe-vpc-peering-connections
aws ec2 describe-route-tables --filters Name=vpc-id,Values=<vpc-id>

Fix

  • Add a route to the other VPC's CIDR via the peering in both VPCs' route tables
  • Allow the other VPC's CIDR (or security group, same Region) in the security groups

Prevent it

  • Plan non-overlapping CIDRs for every VPC up front; use a Transit Gateway for more than a few VPCs

Error text

  • Launch in another AZ, or a similar type
  • Retry later

  • Auto Scaling groups across several AZs and instance types; capacity reservations for critical workloads

403 Forbidden on HeadObject or GetObject

Error text

fatal error: An error occurred (403) when calling the HeadObject operation: Forbidden
An error occurred (AccessDenied) when calling the GetObject operation: Access Denied

Why it happens

S3 refused the request. The CLI's HeadObject cannot show why, so check each layer.

Likely causes

  • No identity policy allows s3:GetObject on that key
  • The object is owned by another account (ObjectWriter ownership)
  • The object is KMS-encrypted and the key policy does not allow you
  • A bucket policy deny, or a VPC endpoint policy

Confirm

  • Set Object Ownership to BucketOwnerEnforced
  • Allow kms:Decrypt in the key policy
  • Grant the action on the right ARN

Prevent it

  • BucketOwnerEnforced on every bucket; one KMS key policy per data set, reviewed

NoSuchKey, or an object that vanished

Error text

An error occurred (NoSuchKey) when calling the GetObject operation: The specified key does not exist.

Why it happens

No current object has that key. In a versioned bucket it may sit behind a delete marker.

Likely causes
